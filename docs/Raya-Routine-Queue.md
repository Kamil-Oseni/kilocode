# Routine occurrence queue: persistence contract

Status: the transactional store and additive database migration are implemented and tested. Timer startup now publishes and reserves a queued occurrence before creating its session. Existing filesystem claims still serialize routine startup; queue, claim, session and history publication are separate writes. Catch-up policy, full recovery and lifecycle handling remain incomplete.

## Records and identity

The existing application SQLite database contains two Raya-owned tables:

- `raya_routine_cursor`: one cursor per routine ID and schedule version. It records the greatest timestamp published in a committed occurrence batch.
- `raya_routine_occurrence`: a selected timer occurrence, its observed time/timezone, execution state, claim/owner, lease, session link and update time. The database enforces uniqueness of routine ID, schedule version and scheduled timestamp independently of the record ID.

Timer IDs use the same deterministic routine/version/timestamp tuple as the trigger evidence already recorded by the runner. Different schedule versions have independent cursors and identities. The queue currently supports timer occurrences; event IDs, interval anchors and full definition snapshots are separate work.

## Publication

New startup attempts save an immutable instruction snapshot before session creation. It is keyed by the run/claim ID under filesystem storage `raya/agent-starts` and contains the selected definition, startup timestamp and resolved objective, including the memory/plan text actually selected. Transient next-run/execution projections are omitted. Identical retries may read the same snapshot; a different value cannot replace it. Snapshot write failure prevents session creation. This is a separate persistence boundary after timer reservation, not an atomic queue/session transaction.

Snapshots preserve the inputs needed for recovery review; they do not currently recreate a missing goal or authorize resuming work. Older runs have no backfilled snapshot. Snapshot lookup verifies identity. Retention, cross-process crash coverage and full versioned output/budget contracts remain open.

`GET /kilocode/agent/:agentID/runs/:runID/snapshot` reads the original snapshot through the authenticated, workspace-routed routine API. The saved routine and run identities must match the request, including the snapshot's embedded definition identity. A current roster entry is not required: retained instructions remain readable after routine removal. Success returns the immutable definition and resolved objective; 404 means no matching snapshot is available, and 400 reports unreadable, invalid or mismatched saved data. A snapshot may exist before run history because it is written before session creation. Reading it does not restore a removed routine, create history, create a goal or resume work. The generated SDK exposes this as `kilocode.routine.snapshot`.

The Routines view's Review runs panel combines recorded results/evidence, the selected conversation and original startup instructions. It uses this API to inspect retained history entries and interrupted startups. Execution preview exposes the persisted run/claim ID when exactly one active timer occurrence exists, even before session linking or history publication. Multiple active occurrences withhold that identity. Without active queue ownership, preview inspects the filesystem startup claim, including manual and event starts. The panel selects the execution identity first and labels entries without history explicitly; it preserves that choice while switching to older history and back. It also preserves selected content across roster refreshes and rejects stale replies after switching runs or retrying. Missing history, results and snapshots are identified explicitly, including startup stopping before snapshot publication. Review remains read-only.

Claim inspection distinguishes startup executing in this process from retained or foreign claims using a process-local set of currently executing claim IDs plus the saved host/PID. Entries leave that set on every completion path, including failure and interruption. The set affects presentation only; filesystem claims remain the exclusion authority. Retained/foreign claims require review, not an assumption that their owner is stopped. Malformed, mismatched or unreadable claims expose recovery state without navigation identities; interrupted reads retain cancellation. Preview never repairs, removes or transfers a claim.

`publish` validates a nonempty batch of at most 256 occurrences. Every timestamp must fit the supported integer date range. An occurrence cannot be observed before its scheduled timestamp.

Publication uses an immediate SQLite transaction. It compares the expected cursor, inserts the batch and advances the cursor together. A stale publisher fails with a typed conflict and publishes nothing. Occurrences must follow the previous cursor. Duplicate identities within a batch preserve the first stored evidence. A failure after an earlier insert rolls that insert and the cursor back together.

The cursor means that the caller published the supplied batch. It does not prove that the caller enumerated every intervening scheduled occurrence. The scheduler integration must supply the complete intended batch or persist an explicit policy decision for omitted work. This store does not silently implement a skip or catch-up policy.

## Execution ownership

| Operation | Required prior state and identity | Result |
|---|---|---|
| Claim | Queued occurrence; nonempty claim/owner; future lease | One conditional update to starting. Only one competing claimant wins. |
| Heartbeat | Starting or linked; matching claim and owner; lease not expired | Extend the lease without shortening it. |
| Link session | Starting; matching claim | Persist the session and move to linked. A later call cannot replace the session. |
| Settle | Linked; matching claim and session | Move to complete and clear the lease. |
| Inspect stale | Starting or linked with an expired lease | Return evidence for reconciliation; do not change state or requeue. |

These methods return whether a conditional transition occurred. A failed/retried transition is not permission to repeat session creation or an external action. Callers must read the occurrence and reconcile its recorded identity/state. Claim IDs are unique per attempt. The runner supplies an opaque process-local owner identity.

An expired lease is not proof that the worker or its external action stopped. The store deliberately does not transfer ownership automatically. Late session-link or settlement evidence from the matching claim remains recordable after lease expiry; a heartbeat cannot revive an expired lease. Complete here means that the queue entry has been settled, not that a business goal succeeded. Goal outcome evidence remains separate.

## Verification

- Real SQLite tests cover atomic publication, stale cursors, rollback after a later batch failure, duplicate identities, version isolation, conditional ownership, wrong-owner/session rejection, lease extension/expiry and immutable session links.
- Independent database connections compete for publication and claiming, then the database is closed and reopened to verify persisted ownership and cursor state. This is not a multi-process stress test.
- Migration tests upgrade the preceding schema while preserving session data, enforce occurrence uniqueness, avoid replay and roll back a failed migration without deleting pre-existing records.
- The migration generator and its drift check run successfully on Windows after correcting native path-separator handling.

## Runner integration

Newly settled outcomes use a nonblank saved blocked reason or audit summary. When neither exists, the summary remains empty so run review can show that no result was recorded. The requested objective is never substituted as an outcome or appended to role memory through this fallback. Recorded evidence remains separate and is preserved even if its summary is empty. Existing historical outcomes and memory are not rewritten because their original provenance is not reliably distinguishable.

When a startup snapshot exists, settlement uses its original role/objective to classify the result and its original memory scope to decide whether to append role memory. The snapshot must agree with the run's routine identity, startup timestamp and schedule version. Invalid or conflicting saved evidence stops settlement before history/memory publication; a dedicated recovery action for this condition is still needed. Legacy runs without a snapshot retain their existing definition fallback. Later routine edits remain available for future runs and are not overwritten by settlement.

The timer first reuses queued work in the current schedule version, including work selected before a restart and now outside the polling window. Otherwise it calculates a due timestamp and publishes it under the existing definition mutation gate. Fresh history excludes pending work and already-consumed legacy occurrences. Old queued versions are not selected after a schedule edit.

Startup acquires the existing filesystem claim, validates the queued identity against current definition/history, then conditionally reserves it before session creation. The same claim and occurrence identities are persisted in session metadata, the filesystem claim, the SQLite session link and run history. Uncertain startup outcomes retain evidence and block another start. Manual and event starts also reject an active timer occurrence.

The timer renews leases only for linked occurrences owned by this process and matched to pending history. It does not renew an orphan starting record. Revival through the routine runner skips foreign or expired queue ownership; legacy runs without a queue row retain their previous behavior. Terminal reconciliation requires matching occurrence/claim/session history and a corresponding terminal goal before settling the queue. List preview reports queued work and active or expired ownership.

General goal resume and turn-close continuation, including provider-error retry, now check queue ownership before changing goal continuation state and again before invoking the continuation runner. The check requires matching routine/version/claim/session metadata, linked pending history, the current process owner and an unexpired lease. Missing database access, malformed routine metadata and mismatched records deny continuation. New timer sessions use metadata version 2 and also deny continuation if their queue row is missing; version 1 timer sessions with no queue row retain legacy behavior.

Manual and event sessions now check filesystem startup claims through the same continuation boundary. A retained, foreign, malformed or unreadable claim denies continuation. During locally executing startup, continuation requires the matching run/session identity, a persisted session link, and pending history with the same schedule version and complete trigger evidence. With no claim, existing manual/event continuation behavior is preserved. These checks apply before continuation counters and before dispatch through the shared goal service; they do not cancel already-running model or tool operations.

Routine list responses now include transient execution state (`starting`, `active` or `recovery`) and the saved session ID when unambiguous. Foreign or expired ownership requires recovery review; multiple active occurrences withhold a session shortcut. The Routines view uses this state to suppress another start, open the matching saved run with **Review run**, or show disabled **Needs review** when no session can be identified. It displays the matching run's stored recovery reason. An unrelated later history entry cannot redirect that action. These controls inspect existing work; they do not authorize ownership transfer or restart.

These checks do not atomically encompass model dispatch or external actions. Lease expiry does not stop an already-running model or tool. A lease can expire after the goal counter write and before the final check: dispatch is then suppressed, but the counter write remains. The queue also has no unique active-per-routine constraint across different occurrences; actual startup relies on the existing filesystem claim in addition to queue checks.

## Required remaining work

`GET /kilocode/agent-archive` lists retained final routine definitions through the existing workspace-routed API. During removal, the archive capture is saved before the cleanup receipt and roster publication, while the mutation gate and startup claim are held. Archive reads use that same mutation gate and exclude every ID still present in a required, valid roster. A failed archive write prevents removal; a capture followed by failed roster publication stays hidden. The archive retains the definition's last configuration but strips computed next-run and execution state. Its `archivedAt` timestamp records the capture time, not proof of an exact deletion-commit time. Results are sorted newest capture first, then by routine ID.

The generated SDK exposes this as `kilocode.routine.archive`. The Routines view's **Removed routines** section loads this list on demand. Selecting a routine displays its final configuration and loads its retained history; **Review retained runs** opens recorded results, evidence, conversation navigation and original startup instructions in the shared run-review panel. Loading, empty, error/retry and missing-history states are explicit. Requests carry a request ID and selected routine ID; stale replies cannot overwrite another selection. The host verifies archive membership before reading a selected history and rejects mismatched identities or invalid timestamps. Review actions do not restore routines or arm schedules.

The archive response is `{ items, next? }`, with up to 50 definitions per page. Pass `next` as the `cursor` query to continue after the last saved entry, or pass `agentID` for a single retained definition. Cursor and direct lookup cannot be combined. Unknown/invalid cursors return an invalid-request response requiring refresh. The cursor follows the saved entry rather than an offset, so entries inserted before it do not shift the next page. This is not a frozen snapshot across requests: changes after the anchor can appear on later pages, while newer captures before it require a refresh.

**Load more removed routines** fetches another page on demand. It preserves the selected routine and existing options when pages overlap, ignores duplicate IDs, and resumes the same page after closure or retry. Direct archive membership lookup lets the host verify an older selected routine without reading every page first. Refresh replaces the displayed list from page one.

Earlier removals without a saved archive entry are not reconstructed. After a one-time legacy import, page reads use the ordering index and retrieve at most 51 archive rows; direct lookup uses the routine ID. New captures update a single indexed record instead of rewriting the archive file. The initial import still reads the complete legacy file, and reads still load the current routine roster for exclusion. Large individual definitions and accumulated UI options are not byte-bounded; bounded retention, purge controls and production-scale measurement remain open. Native visual, keyboard/screen-reader and large-history validation remain necessary. The current UI is a basic retained-work browser, not restoration or deletion-recovery tooling.

Production archive reads and removals now use the indexed store. Migration `20260908124554_kilocode-routine-archive` adds the archive and import-checkpoint tables plus an index on descending capture time and ascending ID. Initialization validates complete legacy definitions before importing entries and their completion checkpoint in one immediate transaction. Invalid/duplicate identities or conflicting indexed evidence roll back the import. Indexed responses are decoded through the full archive schema and checked against their row identity; invalid saved data stops publication. Repeating a completed import cannot replace subsequently updated indexed records.

Import, page reads and removal writes use the routine mutation gate. Removal captures the indexed definition before staging its cleanup receipt and changing the roster; a failed database write leaves the routine/history intact, and a failed roster write leaves the indexed capture hidden. Callers without database access cannot read archives or remove routines; they receive a reconnect error instead of writing a second file-backed archive. The original legacy file remains untouched for recovery, but changes to it after import are not synchronized back into the database. Concurrent older binaries that still write the legacy file and rollback to those binaries are not supported by this transition and require an explicit upgrade/recovery policy. Subsequent new archives must be recovered from database backups, not from the retained pre-migration file.

Sessions recorded in a stopped backend's filesystem claim can now regain their queue link and missing run history. The recovery permit excludes competing repair attempts; the claim, session metadata and queue must agree on routine, version, claim, session and trigger evidence. An unlinked starting occurrence is conditionally linked to that existing session, then reread and checked before history publication. A conflicting session link is never replaced.

If the filesystem claim has no session ID, recovery searches persisted session metadata for the exact routine and claim IDs. Exactly one match is required. It then loads that session through the session service and applies the same full identity checks before repairing the queue/history. Zero matches, duplicate matches, an unreadable session or conflicting evidence leave the claim unresolved and never trigger another creation attempt. Invalid JSON metadata is excluded without aborting the lookup. The query returns at most two rows, but currently has no dedicated metadata index; large-database scan cost remains a performance verification item.

History is inserted only if absent, and retry preserves any existing status/revision. If no persisted goal exists, history records an interrupted-start error requiring recovery review; the current routine objective is not used to invent a replacement goal. Failed queue linking, history publication or claim cleanup leaves evidence for another attempt. Recovery receipts retain the original stopped-owner claim even after successful cleanup. This restores visibility without transferring queue ownership or invoking model work. Live, foreign-host or unprovable owners remain unrecovered.

Polling now retires queued occurrences whose schedule version is older than the current persisted routine version. It rereads that version under the same filesystem mutation gate used by schedule edits and records a skipped state with a replacement reason. This runs for disabled and manual routines too. Current and newer versions, other routines, cursors and already-started occurrences remain intact. Retirement is eventual on a successful backend poll, not part of the schedule edit transaction. Existing startup guards continue to reject stale versions before retirement.

Removal now acquires the same exclusive claim used by startup, inside the roster mutation gate. It refuses unfinished run history, an existing startup/recovery claim, and active queue entries when the task service has its database (as the HTTP runner does). The eligibility check is read-only; the roster write occurs while ownership is held. This prevents removal from erasing the routine during a concurrent start. Disable the routine to prevent future launches while retaining an active run. Removing an idle routine preserves its saved run history and role memory; sessions, snapshots and queue evidence are not deleted. The HTTP contract describes this retention and returns a readable invalid-request response for these guards. This is roster removal, not a personal-data purge or an archive browsing interface.

Removal now saves a pending cleanup record before publishing the roster change. At the start of polling, the scheduler reads those records under the mutation gate and requires a present, valid roster. Only IDs absent from that roster are eligible for cleanup. It marks their queued occurrences across versions as skipped with a removal reason and acknowledges the records afterward. A failed roster write leaves the present routine's queue intact. A failed queue update or acknowledgement leaves a retryable record; reopening repeats conditional updates without changing already-skipped rows. Up to 256 absent routine IDs are processed per poll. The pending-record file is still read in full, and each queue update can affect all queued rows for its routine.

This cleanup preserves active queue rows, history, memory, sessions, snapshots and cursors. It runs even when the roster is empty, but not when the roster file is missing or invalid. It does not infer deletion from arbitrary orphan rows: removals predating the new record format still require an explicit migration/cleanup decision. A pending record for a failed removal remains pending while the routine exists; it never completes that removal autonomously.

Define explicit recovery actions for missing, ambiguous or unreadable session evidence, missing goals and stopped runs, and add execution fencing at the actual model/tool boundary. Bound retained evidence and pending cleanup records. A failed roster write/claim cleanup can retain a claim requiring reconciliation; cleanup receipts do not resolve that claim or make the deletion API retry return its previous result. Existing tests cover selected boundary failures and reopening, not a complete multi-process crash matrix.

Skip, run-once and bounded catch-up need persisted policy decisions, not just a cursor jump. Intervals need a stable anchor and drift policy. Event delivery needs producer IDs and deduplication. Queue/API/UI integration, crash tests at each boundary and a real representative workflow remain open. No exactly-once external side-effect or always-on execution guarantee is made.

## Repeated terminal blocks

The existing three-block circuit breaker now examines consecutive logical runs of the same schedule version, ordered by startup time with ID as a deterministic tie-breaker. All three must have terminal blocked status and the same recorded reason. Waiting for a user answer is an open run and never triggers the breaker. Success, running/waiting, an error, or a different blocked reason interrupts the sequence; errors need their own classified retry/failure policy rather than being treated as equivalent blocks. Rewriting a run does not create another attempt. A late settlement from an older schedule cannot disable the replacement schedule. The pause note explicitly states the consecutive-block reason, and persisted history and enabled state survive reopening.

History publication and the roster pause remain separate writes. Saved history is now the evidence used to reconcile a missed pause: recording a terminal block enforces the counter, polling retries enforcement for every roster routine, and all manual/event/timer starts enforce it before taking a startup claim. The read-only startup check independently rejects qualifying history even if the roster still says enabled. A failed pause write is propagated rather than swallowed, and it prevents that launch. Reconciliation only writes the pause; it never replays a model or external action.

Explicitly setting enabled to true records the IDs of currently retained runs in the definition's optional `blockReset` field, atomically with the enabled state. These acknowledged runs no longer count toward a future block sequence. History remains intact, a failed resume write changes neither the enabled state nor the reset, and reopening preserves a successful resume. Three fresh matching terminal blocks are needed to pause again. Resume also clears the generated consecutive-block note; unrelated notes are retained. Older definitions without a reset use their retained history normally. The reset uses the existing retained-history policy, including pending runs, rather than introducing a separate unbounded execution log.

This does not complete the recovery overhaul. Structured failure fingerprints, error retry/backoff, exhaustive crash/interleaving tests and older-binary compatibility remain necessary. Launch checking does not atomically fence all later model/tool dispatch, and stopping an already active run remains separate from disabling new launches.

Read-only roster preview also derives a qualifying pause from history, returning disabled state, no next occurrence and the pause explanation even while the stored enabled flag awaits repair. Existing notes are preserved alongside that explanation. Timer eligibility and event matching omit such routines. Preview does not write the roster or acknowledge past failures. After explicit enable saves the reset, preview and event matching admit the routine again. The roster explains Enable's effect beside paused routines and associates that text with the button for assistive technology; enabling sends an update without dispatching an immediate run.

## Missing goal evidence at settlement

When a running routine has no available saved goal, settlement records an error with a separate explanation that its result cannot be verified and asks the user to review the conversation and saved startup instructions before starting more work. This is an evidence gap, not proof that an external action failed. The outcome summary remains empty and the diagnostic is not appended to role memory. Repeated settlement leaves the recorded error unchanged. Invalid or unreadable goal data still fails settlement without replacing history or damaged evidence with a missing-record diagnosis.

Unreferenced completed goals expire after 30 days. Expiry now checks retained routine histories and startup claims before deleting candidates. Any goal referenced by retained run history or a linked claim remains available, including completed runs whose queue reconciliation or later review may still need it. An unlinked startup claim makes the reference set uncertain and defers cleanup for all candidates. Malformed or unreadable reference data also defers cleanup with a diagnostic; cancellation remains cancellation. Once references are removed, the original expiry policy applies again. Explicit goal clearing remains a separate action.

This protection scans retained history/claim files when expired candidates exist; it is not an indexed reference catalog or an atomic cross-process garbage collector. Recently retained runs can keep old goals beyond 30 days, so coordinated retention/purge policy and concurrent-writer fencing remain necessary. It cannot restore already deleted evidence. Explicit recovery decisions for incomplete evidence remain unfinished, and the missing-goal diagnostic does not authorize replay.

Expiry is opportunistic maintenance rather than a prerequisite for reading an unrelated goal. A malformed or unreadable goal encountered during the scan is skipped and preserved, with a diagnostic identifying its session rather than dumping its contents. Other valid, unreferenced candidates may still expire. A failed scan or deletion defers remaining maintenance and allows the requested goal to be read directly. Direct reads still validate the requested record and report its errors; cancellation propagates instead of falling back. Cleanup failures can extend retention until a later successful pass and do not imply successful deletion.

## Mutation contention

Routine mutations serialize local contenders per Storage service before acquiring the retained, storage-wide claim. This prevents background scheduling checks from repeatedly reading that claim while its owner waits for the Storage write lock needed to remove it. Other services and backend processes still use the durable claim and stopped-owner recovery; local serialization does not replace that ownership evidence. Waiting callers remain cancellable, failed operations release ownership after their outcome is captured, and cancellation does not replay an operation.

The regression investigation reproduced HTTP failures without overlapping test processes. Tracing showed a successful mutation waiting approximately 4.6 seconds before acquiring the cleanup write lock, followed by immediate filesystem removal. Coverage exercises concurrent real Storage read-modify-write operations, failed-operation cleanup, cancelled waiters, independent stores, and the complete routine HTTP suite. This is a local contention fix, not a change to shared Storage locking or a broader cross-process fairness guarantee.
