# Goal completion evidence

Completion audits refer to persisted tool results. `get_goal` returns eligible result entries with their `callID`, `messageID`, `partID` and `sessionID`, alongside a bounded output excerpt and available status metadata. Goal-control calls and `task` delegation reports are not completion evidence. Collection includes the goal session and eligible descendants, preserving the existing post-goal timing rules.

A completed task call can report only a background-start acknowledgement or a child's summary. Neither establishes the requested outcome. These reports are excluded from both the evidence menu and completion validation; rejection directs the agent to cite the child's underlying work or verification results. Genuine child-session results remain eligible under the same identity and status checks. Task calls still count as workflow activity in turn accounting, so this evidence rule does not disable delegation or classify every delegated turn as idle. Existing saved audits are not rewritten. Current artifact revisions, criterion relevance and human acceptance remain separate verification gaps; this rule does not make every other completed tool result sufficient proof of the full objective.



## Delegation ownership

New task invocations publish their reserved `childMessageID` alongside parent/child session IDs before execution. The evidence collector follows those persisted links through the actual child-session relationships. It requires a unique source assistant and task call, a non-pending post-goal task, and a unique matching child user record created after the goal. Only assistant results answering authorized inputs enter the child evidence scope. Further task links must originate within that scope.

Other inputs in a reused child session do not become goal evidence. A child session may predate the goal when its verified invocation input is new. Unlinked descendants are not read merely because they appear in the session tree. Duplicate message identities or ambiguous task call/part IDs cannot authorize descendants. An explicitly empty root input list authorizes no evidence. When root input history is recorded, root evidence is similarly limited to assistants answering those recorded inputs. Legacy goals without root input history retain post-goal root-result behavior; that remains weaker than explicit ownership.

Older task results without a child input ID cannot authorize child evidence through this path. Obtain fresh verification in an owned root input or a new explicitly linked task invocation. Delegation metadata establishes execution lineage, not semantic relevance to a requirement, artifact freshness, or human acceptance. Existing accepted audits are not rewritten.

## File revision checks

New `write` and `edit` results retain a `rayaRevision` snapshot after formatting and encoding. Capture streams the resulting file through the sandbox-aware filesystem service, recording its absolute path, resolved target, SHA-256 digest and mode. File identity and timestamps are checked around the read to reject observed concurrent changes. Failed capture records an unavailable snapshot without converting a successful edit into a tool failure; interruption still propagates.

`get_goal` exposes the recorded snapshot as `artifact`; listing historical evidence does not rehash every file. When a completion audit cites a tagged write/edit result, validation resolves the path again and checks its target, bytes and mode. Changed, deleted, malformed or unavailable revisions cannot complete the goal. A change to an unrelated file does not invalidate this result. Recovery requires a fresh eligible result; historical evidence is not rewritten.

New `apply_patch` results record a bundle covering the final state of every affected path after formatting. Added, updated and moved-to files use the same content checks. Deleted and moved-from paths retain an absence observation anchored to their resolved parent. Recreating either as a file or directory invalidates the bundle. Parent directory listing detects even dangling link entries; a failed listing or changed resolved parent cannot prove absence. Name comparison conservatively ignores case, so a case-only sibling can prevent absence verification even on a case-sensitive filesystem. Multiple changes to the same path record its last expected state. All bundle entries must validate; empty and malformed bundles are rejected.

New file `read` results also retain a revision, allowing fresh inspection without modifying the file again. The read wrapper fingerprints the same authorized open handle used for text extraction or attachments before and after inspection. Both digests must agree, alongside handle identity, size, mode and nanosecond modification/change timestamps; the requested path must still resolve to the authorized target. Content comparison is necessary because the same-size mutation test reproduced unchanged handle timestamps on Windows. An observed change makes the revision unavailable while preserving the read output; it cannot serve as current completion evidence. Fingerprinting adds two full streaming passes over the file, uses bounded memory, and propagates Effect interruption and tool cancellation. Large-file latency needs measurement and optimization without losing the binding to inspected bytes.

Partial reads retain their existing line-range/truncation metadata. Their digest covers the file bytes, including undisplayed content, so later changes outside the displayed range invalidate the revision too. The digest does not imply that the model inspected every line, every extracted document feature or every attachment detail. Directory listings remain untagged. Permission checks and binding of the authorized handle still precede inspection and fingerprinting.

This is a bounded observation, not an atomic filesystem fence extending through the goal save or across a multi-file bundle. Existing untagged results retain their previous behavior. Command/build results, dependency graphs and external artifacts do not yet receive this revision check. A matching file proves neither its correctness nor criterion relevance or human acceptance. Previously accepted audits are not continuously revalidated.

## Resolving a reference

The evidence menu also includes an `inspection` summary for reads, independently of `artifact`. Valid text display metadata exposes the displayed line range and reported line count. Offset, line-limit or truncation evidence is labelled `partial`; a fully displayed text presentation is labelled `displayed`, with full review explicitly not established. This does not claim that every document feature was extracted or that a person reviewed it. Missing, legacy or inconsistent display metadata retains unknown coverage; directory results are identified as listings. The menu does not perform a fresh filesystem check. Original-result archival, fuller artifact previews and long-term audit history remain open.

A unique `callID` remains sufficient for existing callers. If more than one stored result matches the supplied identity, completion is rejected as ambiguous. Supply the `messageID` and, where a message itself contains repeated call IDs, the exact `partID` from `get_goal`. An optional `sessionID` must also match. The validator applies all supplied identity fields together; it does not choose the first result or prefer a successful result among collisions.

After resolving exactly one result, the existing checks still apply: it must be completed, be eligible for this goal, and meet the applicable successful-command or browser-smoke requirements. Selecting an exact failed result cannot turn it into passing evidence.

Accepted audits retain the resolved message, part and session identity even when the submitted reference used only a unique call ID. This preserves which stored result was actually validated. Rejected attempts retain the submitted references and rejection reason. Existing saved audits are not rewritten.



## Reviewing a cited result

Expanded current and historical goal details offer **Copy goal report**. The Markdown report contains the selected goal's saved objective, status, criteria, latest audit verdict, evidence identities and available result digests. Copy success is shown only after the extension host acknowledges the clipboard write; failure can be retried, and changing the selected goal discards late feedback. Missing historical records are stated explicitly. This is a saved-record report, not a fresh verification, original-output archive, cost statement or complete deliverable inventory.

Newly archived goals retain their own execution counters and accumulated active time. Reports include these saved values when available and identify missing legacy counters. The recorded active duration excludes any currently running interval not yet accumulated in storage; counters and duration are not token or monetary cost estimates. New goals start with their own counters rather than inheriting history totals.

The existing browser-smoke completion gate also checks the matched saved criterion's verification instructions. A recognized requirement for a passing smoke test needs a successful `browser_smoke_test` result with the existing host evidence marker; a successful unrelated command cannot substitute for it. This is the existing smoke-specific rule, not a general interpreter or proof of arbitrary verification prose.

Changing the current goal's objective invalidates its accepted audit and latest completion attempt. They are not displayed as evidence for the revised direction. Status-only edits preserve the attempt, and saved acceptance criteria remain unchanged by objective steering. This is not a revision-history archive: obsolete attempts are removed from the current goal record rather than retained as a separate version.

Expanded goal details display saved acceptance criteria with their stable IDs, descriptions and verification methods. Audit entries identify their criterion when one was recorded. Starting a new goal retains the completed goal's original criteria alongside its audit in recent history; historical review displays that saved contract rather than the current goal's requirements. Earlier history entries without criteria remain readable, but their original acceptance contract cannot be reconstructed by this change. Criteria remain subject to the existing last-20 history retention policy.

The source viewer now presents recorded read coverage directly above the input/output preview, using the same shared classifier as the model-facing evidence menu. It identifies partial displayed line ranges, the reported line count, directory listings, empty text extraction and unknown coverage. A fully displayed text range remains distinct from a full review or a current-file check. These labels are derived from the exact retrieved result's structured metadata, rather than inferred from its output excerpt. Non-read results do not receive an inspection label.

When a completed goal is replaced by a new goal, its accepted audit and latest audit attempt now remain in the existing recent-history record, including evidence receipts. The new goal starts without inheriting those audits. The extension's previous/next goal controls display the selected historical audit; older history entries without retained details explain that no audit is available. Current execution controls and activity remain tied to the current goal.

Source requests carry the selected goal's creation time. The backend client resolves exactly one matching current or retained historical goal and checks only that goal's references and accepted receipt. Missing or ambiguous history selection fails without fetching a source message. Requests without selection retain current-goal behavior for compatibility. Changing the selected history entry resets the source view and ignores late replies.

Retention remains bounded to the existing last 20 completed goals in the session. Older entries already stored without audits cannot be reconstructed by this change. Clearing/expiry and history eviction still remove access to these retained records; a separate long-term archive and policy are not implemented here.

New accepted evidence references retain a host-generated `record` containing version, SHA-256 digest and observation time. The digest covers the persisted tool name and state, including input, output, metadata and tool timestamps, using deterministic object-key ordering. Validation discards submitted receipt fields before accepting or rejecting an audit; callers cannot supply their own verified-content claim. Accepted receipts survive goal reload. They fingerprint the result content rather than copying it into another archive.

When reviewing an accepted reference with a receipt, the extension recomputes that digest from the exact fetched result. A mismatch produces a changed-source error; a match is labelled as matching the accepted audit's recorded result. Older or rejected references without an accepted receipt remain explicitly unrecorded. This is a consistency check, not a signed attestation, a fresh artifact check or proof of semantic relevance. It cannot recover original content if the transcript is edited or removed. Retained original-result archives and immutable history remain open.

The extension audit panel offers **View source** for references with saved session, message, part and call identities, including child-session evidence. The backend client first rereads the goal and requires that the selected current or retained historical goal's audit or audit attempt still contains that exact reference. It retrieves the named message and requires one matching tool part, checking both message and part identity. Missing, duplicated or mismatched records produce an explicit error rather than selecting a substitute. Legacy references without complete identity remain visible with an explanation.

The inline viewer shows recorded tool status, input, output and metadata as plain text. Each field is capped at 50,000 characters with a truncation notice; scrollable content is keyboard focusable. Opening a result performs GET requests only. It does not rerun a tool or assert present artifact freshness, criterion sufficiency or human acceptance. Replies are matched to the owner session and request ID, ignored after close or session change, and a timed-out request can be retried. The viewer stays in the audit rather than changing the active conversation. Runtime visual inspection in packaged VS Code, richer artifact rendering, long-term archival and command-specific verification remain separate work.

## Criterion coverage

Goal continuation no longer mandates a task call for every agent. Its shared reminder asks the current agent to choose a concrete action, use available direct tools where appropriate, and delegate only when authorized and useful or required by its routing role. It conditions task-list updates on tool availability and asks for progress grounded in evidence or changed outcomes. This prompt guidance does not change tool permissions or replace the existing runtime accounting heuristic. Auto still has its Chief routing prompt and restricted tool set; giving Auto a broader direct-execution lifecycle remains part of the separate Auto overhaul.

Routine goals with saved criteria also require exactly one audited requirement for each criterion ID, preserving its description. Each requirement must pass the evidence checks above. Additional requirements from the broader objective remain allowed. The routine output and criterion workflow is described in [Routine scheduling](Raya-Routine-Scheduling.md).

## Concurrent goal updates

Every goal save now assigns an opaque revision. A writer must still be based on the stored revision and creation identity when it commits. The comparison and atomic replacement run under a per-goal filesystem mutation gate; evidence collection runs outside that gate so steering can proceed while validation is underway. A stale successful completion or rejected-audit write fails without replacing the newer objective, pause state or audit context. Clearing a goal also uses the gate, preventing a stale operation from recreating it.

Expiry cleanup acquires the same gate and rereads each candidate before deletion. It removes the record only if it still matches the inspected expired state. This does not make the separate routine-reference scan and goal deletion one transaction.

The gate reuses the existing claim and stopped-owner recovery protocol in a distinct goal namespace. Flattened hashed keys avoid nesting long hashes on Windows. A live owner is not stolen because it is slow; an unavailable gate produces a bounded busy error. A subsequent operation can recover a stopped writer's gate without replaying the old operation. This protocol applies to cooperating current backends, not older binaries or direct filesystem writes that ignore it.

Legacy records without revisions acquire one on their next save. Existing records are not rewritten merely by reading them. A stale operation must reread the current goal and reassess its work; this is not permission to replay an old completion audit.

Automatic continuation now rereads the goal after the routine-ownership permission check. It dispatches the current objective only when the goal still exists and is active. A pause or deletion visible at that check suppresses dispatch. A failure from dispatched work is tied to the revision that launched it; it cannot block a goal that was subsequently revised. An unchanged failed dispatch retains the existing blocked-goal behavior. The revision precondition used for this failure update is internal to the service, not a new public model/API parameter.

Goals also carry an opaque control revision (`intent`). Creation, steering, pause and resume assign a fresh value; ordinary turn/retry/continuation accounting preserves it. Restoring an earlier objective or pausing and resuming still changes this revision. The field distinguishes changes in direction from changes to counters; it is not a complete versioned history of requirements.

Automatic turn, error-retry and continuation accounting may retry a recognized storage-revision conflict up to twice. Each attempt rereads state and checks the captured control revision inside the accounting operation. A changed revision suppresses the stale operation. Persistence errors and other audit errors are not retried. Completion audits and provider dispatch are not included in this retry policy. Older goals without a control revision retain single-attempt behavior until creation or a control change assigns one.

The goal update API now accepts an optional `expectedIntent` control revision. It compares the reviewed value before deriving an edit, and its final write still uses the storage-revision guard. `"unset"` represents a reviewed legacy goal without a control revision. Stale preconditions return HTTP 409; invalid edits return 400. Changing objective and status in one request now commits one goal record rather than applying the two changes separately. A combined pause/edit does not schedule automatic resume. Clients that omit the precondition retain unconditional edit behavior, subject to the concurrent-write guard.

The extension steering editor captures the control revision with the objective when the draft opens. Polling preserves both. Its dedicated request includes a correlation ID and the captured revision; the bridge validates the request and confirms the saved objective, control revision and basic state before acknowledging success. Blank or unchanged drafts cannot be submitted. The editor remains open and read-only during saving, and closes only for a matching confirmation.

Conflicts, connection failures, mismatched responses and a 15-second uncertainty deadline leave the draft visible and disable another save. The user can copy it, cancel and reopen to review the latest goal; there is no automatic retry or silent change of precondition. Late replies are ignored. A reply cannot replace a different control revision the panel observed while saving. An unavailable goal read preserves the draft without claiming that the goal was deleted. Closing the editor restores focus to Steer when that control remains mounted.

Pause and resume now use the same conditional request channel, carrying the saved objective, reviewed control revision and requested status. The panel disables competing controls while awaiting confirmation and requires the returned status to match. Conflicts and the 15-second uncertainty deadline request a fresh read without automatically retrying the write. Late replies cannot acknowledge an expired request. Pausing with an open steering draft preserves that draft and requires copy/cancel/reopen before saving against the changed goal.

This does not persist drafts across a webview reload or session switch, and the copy/cancel/reopen recovery is not an inline merge workflow. These checks do not atomically fence the later provider call or external effects; recovery after accounting commits also remains open. Generated-SDK and rendered-component tests cover conditional status payloads, rejected confirmations, conflicts, timeout refresh, late replies and draft preservation. Native and packaged-extension validation remain open.

The domain `clear(sessionID, expectedIntent)` operation supports conditional deletion. It reads and compares the control revision inside the same per-goal mutation lock as removal. A stale revision, replacement goal or already-absent record returns a conflict; accounting-only changes preserve the reviewed control revision. The `unset` sentinel matches only a legacy record without an intent revision. Existing internal cleanup calls can still omit the precondition. HTTP DELETE accepts an optional `expectedIntent` query parameter and returns 409 for conditional conflicts; the generated SDK forwards this parameter and exposes the conflict response. Empty preconditions are rejected. The Stop and completed-goal Dismiss controls capture the reviewed revision when confirmation opens. A dedicated goalStop/goalStopped exchange carries session/request identity and requires an explicit successful deletion response. Controls remain disabled while pending. Conflicts or the 15-second uncertainty deadline preserve the visible goal, request a fresh read and require cancellation/review before retrying. Late replies are ignored, and a successful acknowledgement cannot hide a different goal revision already observed by the panel. Removing tracking does not cancel an already-dispatched external operation.

## Turn accounting

Pending or running tool parts suppress continuation without advancing accounting or consuming a receipt, including pending goal-control tools. Once a terminal result is available, accounting can inspect that message again. This state check does not prove that an external handle is still alive; reconciling stale tool state against actual operations remains required recovery work.

A turn with no successful work-tool result uses the existing bounded recovery counter rather than resetting it merely because a tool was called. Completed shell calls require numeric exit code zero; failed calls, unknown-tool errors and shell results without that exit evidence do not qualify. Three consecutive idle/failure-only recovery turns block with a reason; identical repeated work may stop earlier. A successful result resets the counter, and all attempted work-tool calls remain counted in usage. The counter is shared with provider-error recovery.

Resuming a paused/blocked goal or changing its objective resets consecutive retries and clears the old blocker when work resumes. Usage totals and consumed event/message receipts remain intact, so an old error notification cannot consume the renewed budget. Pausing alone, submitting the same objective, or setting an already-active goal to active does not reset the counter. The same policy applies to direct controls, conditional API edits and model resume actions.

This is a failure-aware heuristic, not criterion-level proof of progress. A completed generic tool may still return irrelevant information or a domain failure in its text, and a successful read is not necessarily an advance toward the objective. Artifact revisions, semantic verification and operation-level waiting remain part of the overhaul.

Successful session-loop exits attach the returned assistant message ID to the turn-close event. Completed-turn accounting rejects an identified event unless it matches the latest assistant of the current user turn. The goal stores the current user ID and accounted assistant IDs atomically with its usage update. Repeated events return no continuation decision, including after service recreation. Concurrent copies cannot both commit because the goal revision check rejects the stale writer.

A retry that adds assistant messages to the same user turn counts only the new messages and their tool calls. When a new user turn is accounted, its receipt replaces the prior user's receipt. Legacy callers without message identity still deduplicate the current transcript, but cannot distinguish an old notification from a new turn that has not yet been accounted. Legacy saved goals acquire their first receipt on their next accounting write; prior usage is not reconstructed.

Provider-error notifications use a separate receipt containing consumed bus-event IDs. Receipt and retry counters are saved together with the goal revision. Duplicate detection runs before enforcing the retry limit, so replaying the third allowed retry does not block the goal. A distinct subsequent error blocks without incrementing continuation counts. Receipts survive resume and service recreation and remain with the goal until it is cleared or expires. Legacy callers without event IDs retain their previous behavior; distinct event IDs representing the same underlying provider failure are not coalesced.

A crash between saving accounting and dispatch can still leave work awaiting recovery; these receipts are not an exactly-once dispatch or external-effect guarantee. Conflicts that exceed the bounded accounting retry policy stop that callback. Recovering an interrupted dispatch remains separate work.

Continuation accounting now atomically saves a dispatch ID, reviewed intent, queued timestamp and `queued` phase in the goal record. Provider-error retries save the same information with their retry receipt and counters. Before calling the runtime, the launcher conditionally changes that exact dispatch to `started`, recording a handoff timestamp. Only one contender can make that transition; a consumed, replaced, paused, deleted or differently steered dispatch cannot be launched by the old callback. Failure blocking uses the post-claim storage revision. A `started` record means the handoff was attempted, not proof that a provider or external tool is live. Workspace initialization now attempts the bounded recovery path described below; unconfirmed started records are never assumed stopped. The goal record retains only the latest dispatch, so full operation history remains separate work.

Each new dispatch also reserves a user `messageID` in the same accounting write. Claiming preserves it, and the default launcher passes it to `SessionPrompt.prompt`, whose existing input contract uses that ID for the saved user message. A legacy queued record without an ID receives one in its guarded claim before handoff. Retry-event replay cannot allocate another ID. This provides an exact conversation lookup key for future reconciliation; the presence of a reserved ID alone does not prove that the message was saved, the provider started or external effects completed. No automatic prompt replay is introduced.

Completed, error and interrupted turn-close notifications now acknowledge the matching dispatch before checking whether the goal remains active. A started dispatch can become `finished` only when its reserved user message exists, the notification names the latest assistant replying to that user, the assistant has a finite completion timestamp at or after handoff, and no matching reply contains a pending/running tool. A completed outcome requires no assistant error; an error outcome requires a saved assistant error. The record stores that assistant ID, completion timestamp and outcome. This guarded acknowledgement preserves objective, control revision, goal status and counters, including when the user already paused or steered the goal. Duplicate or older acknowledgements cannot finish another dispatch. Failed loop exits attempt to identify the saved closing assistant. A failed read is logged and leaves the message identity absent; it does not fabricate an outcome. Superseded notifications still do not use this path. The marker corroborates a terminal conversation turn, not fulfillment of goal criteria or independently verified external effects; live external-operation reconciliation remains open.

Before claiming queued work, dispatch reads the session conversation. It leaves the record untouched if the reserved message already exists, or if a user message sorts after the reserved ID or was created after the dispatch was queued. Newer assistant messages alone do not supersede user intent. A failed conversation read cannot authorize a handoff. This preflight prevents known saved prompts or newer user input from being overwritten/superseded; it does not atomically lock conversation insertion with goal claiming. The goal prompt writer now repeats the conversation checks in the durable message transaction, as described below. An existing prompt is not treated as proof of a live worker, and an absent prompt is not proof that all earlier external effects stopped.

The durable event service now provides a local `prepare` publication hook for that insertion boundary. It runs inside the existing immediate SQLite transaction before any projector, followed by the existing commit hook, event persistence and post-commit notification. Failed preparation rolls back its database writes and consumes no event sequence. Live-only events reject the hook. It is not serialized or supplied during replay. Actual SQLite tests verify competing conditional publications admit only one winner and rejected preparation neither projects nor notifies. The goal prompt writer uses this hook to reject an existing reserved message ID or newer user input before the message upsert and durable event write. The automatic runtime handoff carries the queued timestamp with the reserved ID; these are internal prompt inputs, not HTTP request fields. A duplicate/superseded insertion ends that handoff without starting a model turn or consuming another recovery attempt. Invalid reservation identity remains an error. Actual no-reply prompt tests verify the reserved message and text parts save once and remain unchanged after duplicate or superseded insertion attempts. Parts retain their existing separate write lifecycle; message insertion is not proof that all parts or external work completed. The transaction guards conversation insertion, not a cross-store transaction with filesystem-backed goal steering or pause.

Current turn-close events carry `goalIntent`, captured before the session loop starts. Error recovery ignores a captured revision that differs from the current active goal, so an error from before steering or pause/resume cannot consume the new direction's retry budget. The explicit `none` marker means no active goal could be attributed at turn start, including missing, paused or unreadable state; `unset` denotes a legacy active goal without a revision. Capture failures are logged and do not modify the stored record. The marker uses a string because the generated event contract omitted nullable values. Older events without this field retain legacy recovery behavior and cannot provide the same direction guarantee. This change does not bind completed-turn evidence to semantic criteria, or cancel external work after steering.

## Workspace startup recovery

Workspace initialization starts a detached recovery scan after registering goal continuation and routine lifecycle handling. It enumerates persisted goal keys, resolves each session, and only considers active goals with dispatch records in the current workspace. The continuation setting and the current runtime's idle check gate recovery and are checked again immediately before handoff. Disabled continuation, other workspaces, paused goals and busy sessions remain untouched. Missing/corrupt sessions are logged and isolated so other entries can recover; interruption propagates.

The scan uses the existing resume path and conditional dispatch claim. Repeated scans cannot replay a consumed queued identity, and unconfirmed started attempts are preserved. Eligible completed evidence can recover through acknowledgement/accounting. Each scan processes at most two recovery entries concurrently, and all scans in the backend share a two-permit recovery semaphore. One long-running resumed turn therefore leaves a slot for other entries; two occupied slots retain the rest in the queue. An unavailable entry releases its slot after logging. The current process's idle check is not a cross-process execution lease, and its observation is not atomic with handoff. The shared permits bound recovery entries across repeated scans and workspaces in the same backend. They are released by Effect when an entry finishes, fails or is interrupted. This is not a cross-process lease or a bound on independently running tools after interruption; external-handle reconciliation and ownership across backend processes remain open.

## Dispatch-to-worker binding

At the start of the actual committed run loop, an owned hook observes the running worker and attempts to save its ID in the started goal dispatch. Binding requires the exact dispatch identity, its reserved user message as the latest user by ID, and no other user created after the queue timestamp. It does not infer ownership merely because a session is busy. Existing worker bindings cannot be replaced, repeated binding to the same worker is inert, and usage/control intent are preserved. The field is optional for legacy records.

For an active goal without a dispatch, initial ownership requires its saved `startMessageID`. A client-armed goal anchors to its first user message. A goal created by the model anchors to the currently unfinished assistant message and resolves its parent user. That user must still be the latest input, the control intent must match, and no newer input may supersede it by timestamp. Missing anchors, completed assistant anchors, paused goals and existing dispatches cannot authorize a new initial binding. The initial started dispatch records the actual observed worker without charging a continuation or replacing the original review/discard anchor.

The `create_goal` tool uses the same association helper immediately after goal creation, so a goal created during a running turn need not wait for a later model step to acquire ownership. The shared tool registry supplies the actual session run-state service through a narrow dependency hook. Once the initial dispatch finishes, the existing evidence and continuation machinery applies; its first automatic continuation receives a new dispatch/message identity and increments the continuation count once.

Binding failures are logged without fabricating ownership or stopping otherwise authorized work. Cancellation or completion does not erase the association. The saved UUID is evidence of the worker observed at binding time, not a durable cross-process lease or proof of current liveness. Goal stop/recovery must still re-query and compare the current handle and protect newer input before cancelling it.

## Conditional running-worker cancellation

Prompt intake serializes its message-creation work through a per-session input gate in this backend. A second intake cannot insert its message while the first holds the gate; other sessions remain independent. Cancellation releases holders/waiters and unused gate entries are removed. Reviewed goal-stop requests use the same gate while checking conversation ownership and selecting cancellation. This covers the prompt creation path, not every low-level message mutation or another backend process. Model execution occurs after intake and does not hold this gate for the whole turn.

The internal run-state service can cancel a running execution by its observed ID. The identity comparison and selection of the handle occur inside the runner's synchronized state update. A stale ID, idle state, shell or queued request returns false and leaves the state untouched. A matching running handle is removed from current state, interruption is requested for its exact fiber, and its completion waiter is settled using the existing cancellation error. After waiting, the method checks the fiber's actual exit and reports interruption only when the exit carries an interrupt cause. A worker that finishes before cancellation executes is not reported as interrupted. The method does not cancel a replacement run or enumerate/cancel background jobs.

Running work also receives its own execution identity through Effect context, derived from the same completion handle used by observation. Nested runners install their own identity; returning from them preserves the parent's context, and callers outside a worker receive no identity. Goal association now requires this executing identity to match the current observed worker before binding either an initial or continuation dispatch. An older worker cannot adopt a replacement worker merely by inspecting the session after replacement, and an outside caller cannot establish a binding from transcript/state observations alone. The prompt-to-worker binding described below uses this process-local identity.

Reviewed goal-stop requests check the expected control intent under the goal mutation lock and the current input under the input gate. They clear tracking and first select a retained started dispatch with a saved worker and reserved user message that is still the latest input. After releasing those locks and awaiting that cancellation, Stop also checks the shared prompt-worker registry against the goal's recorded input history. This can stop an earlier goal input when a later dispatch is queued or unrelated user input has been saved. Selection requires the worker's actual current binding to match an owned input; a worker that has advanced to unrelated input is preserved. The runner atomically rejects stale worker identities. Shells and missing bindings cannot authorize this additional cancellation. Legacy clear requests without an expected intent retain tracking-only behavior.

Cancellation selection returns a wait handle after starting cleanup in the runner's owning scope. Stop releases the goal/input locks before awaiting that handle, so worker finalizers can acquire those locks without deadlocking. Waiting to acquire the input gate remains interruptible and leaves tracking untouched if abandoned. Once selection has committed, interrupting a request waiter does not cancel the cleanup request.

Stop results are persisted separately under `raya/goal-stops/<session>/<hashed-intent>`. The `requested` record is saved before tracking removal; `cleared` is saved after removal and before cancellation selection; `finished` records the observed interruption result and completion time. Publication of the final result runs independently of the HTTP waiter. The parent interruption field alone does not establish termination of delegated work or external effects.

Receipts now also retain `operations`: delegated cancellation attempts identified by attempt ID, job ID, observed registry revision and, for an individual invocation, its reserved child-message ID. Each attempt is saved as `requested` before calling the registry. Only after that call returns is the same entry replaced with an `observed` entry containing its time and registry result. The final receipt update reads the latest saved receipt under the goal mutation lock, preserving all attempts rather than overwriting them with the earlier cleared snapshot. These writes do not hold the goal lock while waiting for worker cleanup.

A failed request-record write prevents that delegated cancellation call. If the call runs but saving its result fails, the durable request remains without an observed outcome and the background observation is marked unavailable. Even a `finished` overall receipt can therefore contain an unconfirmed delegated attempt. Reopening or replaying that receipt reads the saved evidence without reissuing cancellation against a replacement job. The HTTP schema and generated SDK preserve both requested and observed entries; older receipts without this field remain valid.

The immediate confirmation and reopened history display those saved attempts. An input result of `accepted` means the registry accepted cancellation, which may only have prevented queued work; it is not an external-termination claim. Whole-job outcomes are labelled as registry reports, and a requested entry explicitly says no result was recorded. Invalid or conflicting result shapes produce an unverified notice. Full reconciliation after a backend crash, durable external-operation handles, retention and a browsable history remain separate work. Attempt arrays currently stay with their receipt and are not truncated; scaling their repeated atomic writes requires an archival policy that preserves evidence.

Finished receipts from reviewed HTTP stops also retain a dated background-job observation after parent cancellation and the delegated cancellation pass settle. The read-only observer follows registry `parentSessionId` / `sessionId` relationships, including completed intermediate jobs, and records the ID, type and title of related jobs still running in that snapshot. Relationships alone are not proof of cancellation ownership. A registry or delegated-settlement failure produces an explicit unavailable observation, distinct from a successful empty check. Older receipts without observations remain readable.

Both immediate stop confirmation and reopened stop history display the observation. Job titles are rendered as text. The wording describes work running **at the stop check**, not current liveness; retries retain the original observation. Coverage is limited to relationships still present in this backend's instance-scoped registry. Jobs in another process, evicted relationship metadata, external requests and jobs that start after the check are not covered. Cancellation across the full goal lifetime, durable operation ownership and reconciliation remain open.

The background registry now provides process-local cancellation prerequisites. Each admitted start has a fresh revision, and each admitted extension changes it under the registry lock. `cancel(id, revision)` compares a supplied revision under that same lock and returns no result when it is stale. This prevents an observation of an earlier generation or smaller set of admitted work from cancelling a replacement or extension. Callers must require a defined observed revision before using this path; legacy `cancel(id)` remains unconditional. A completed matching job retains its completed status rather than being reported as cancelled.

Task starts and extensions also record their parent session, assistant-message ID and tool-call ID when available. Every admission is retained, including unknown origins, and snapshots copy the origin records so callers cannot rewrite registry ownership. The cancellation resolver corroborates these identities against persisted task calls as described below. The receipt retains a snapshot of related work still outstanding after cancellation.

New task admissions additionally reserve the child session/message pair before entering the registry. The same reserved message ID is passed to the eventual child prompt, including extensions waiting behind earlier work. This distinguishes invocations that share a child session and supplies an exact edge for later traversal of nested ownership. A reservation proves neither that the child input was persisted nor that a worker started; older origins may lack this pair and cannot establish that edge. Runtime coverage compares recorded pairs against the actual prompt inputs for both initial and queued work.

The prompt loop now binds its selected, queue-scoped user message to its executing worker before tool/model work. The prompt service and reviewed HTTP goal handlers share one instance-scoped worker service through their dependency graph. Bindings are keyed by execution identity, and cleanup removes only that identity. Task cleanup supplies its reserved child-message ID to the prompt service. Cancellation compares the current worker's bound session/message under a synchronized binding lock, selects exact runner cancellation, then releases the binding lock before awaiting cleanup. Goal Stop records its whole set of owned inputs in one registry update and selects the current worker once. A later input on that worker or a replacement worker with a different input is preserved.

Cancellation intent is retained even if the reserved prompt has not started. A subsequent binding attempt for that session/message is refused and the loop interrupts before model/tool execution. These cancellation records live only in the workspace instance and remain until that instance is disposed; they are not a durable recovery ledger. Foreground cleanup also supplies the observed background-job revision, preserving extensions admitted after the foreground job snapshot. These protections do not recall external effects.

Reviewed Goal Stop seeds delegated ownership from the goal's saved bound-input history, plus the retained started or finished dispatch for compatibility. Initial and continuation worker binding append the root user-message ID atomically with the worker binding; scheduling a continuation alone does not add ownership. Repeated binding does not duplicate history. Pause, steering, retries and subsequent dispatches preserve these identities, while a newly created goal starts without the preceding goal's inputs. A matching legacy binding can record its current corroborated input, but does not reconstruct older turns.

Stop still requires the current reviewed control revision. Each saved root must still exist as a user message in that session before it is used. Each admitted origin is checked against exactly one persisted assistant and task call, parented by an authorized input, with matching session/message/call identities and child-session metadata. Cancelling an entire job requires every origin to pass. A verified origin can also authorize its exact reserved child input as an edge to descendants when the parent job contains unrelated or unknown extensions. This preserves the mixed parent's scope while allowing cancellation of fully owned descendants. An unverified origin that claims the same child-message ID prevents that edge from authorizing descendants. Missing, ambiguous and foreign origins never grant ownership. Traversal repeats until no new input edges are established, including when descendants appear before their mixed ancestor in the registry. A job extended by multiple recorded turns of the same goal can still be fully owned, even while the next dispatch remains queued.

Selected running jobs are cancelled using their observed revisions. For mixed jobs, Stop instead selects the verified child-message IDs through `cancelInput(id, revision, message)`. The registry checks the observed revision and requires one matching invocation under its admission lock. A changed revision, reused job ID or duplicate input identity rejects that selection. The resolver then reads again, allowing a newly observed mixed revision to cancel only its verified inputs while preserving newly admitted unrelated extensions. Each revision/input pair is attempted once per settlement pass. After cleanup, the resolver also includes descendants admitted before that invocation finished. The saved stop receipt is replayed without another cancellation pass. The client labels the worker outcome as the parent's outcome, since child invocations may also have been cancelled.

Each admitted invocation has its own cancellation control inside the shared job scope. A queued selection records cancellation without running that input or waiting for unrelated preceding work. The queue still waits for its predecessor before skipping the selected invocation and releasing the following extension, so cancellation cannot let later work overtake an earlier input. A running selection signals only that invocation and waits for its finalizers outside the registry lock. The task wrapper's interruption finalizer cancels its exact reserved child prompt. Abandoning the cancellation waiter does not abandon the job-owned cleanup. Individual cancellation leaves unrelated pending extensions alive; ordinary errors retain the existing whole-job failure behavior. Once all remaining work settles, the aggregate status follows the latest admitted invocation's outcome, and output remains the latest successful invocation's output. Aggregate status is not a durable per-invocation history.

Coverage remains incomplete when earlier turns predate recorded input history, never established a binding, or no longer have corroborating transcript records. Queued-only goals without prior bound inputs may still have no usable seed. Historical inputs now support both parent-worker and delegated-job selection; the parent result combines observed interruption from the retained-dispatch and shared-input checks. Mixed invocations without a unique corroborated input remain preserved. Invocation controls are process-local even though the cancellation request and returned registry outcome are now journaled; neither acceptance nor a final registry snapshot proves termination of external effects. The input history is retained for the active goal's lifetime without truncating ownership; scalable archival and pruning require separate settlement evidence. Other-process jobs, external effects and automatic reconciliation of uncertain cancellation attempts remain open. Preserved related jobs remain visible in the final snapshot; an unavailable observation does not establish termination.

Retries with a `cleared` or `finished` receipt return it without reissuing cancellation or mutating a newer goal. A `requested` receipt with a still-current goal may retry the guarded removal. If tracking is already absent, it advances to `cleared` with an unconfirmed worker outcome and does not cancel anything. A failure to save the first receipt leaves tracking intact. A failure after removal retains an uncertain receipt rather than inventing successful termination. These are guarded separate writes, not a cross-file transaction or cross-process worker lease.

`POST /session/:sessionID/goal/stop` requires the reviewed intent and returns the saved receipt. The extension validates its session, intent, phase and result fields before reporting confirmed interruption, no worker interrupted, or an unconfirmed outcome. The legacy DELETE response remains a boolean tracking-clear acknowledgement; repeating a reviewed DELETE can now confirm the saved removal without affecting newer work. Unversioned DELETE retains tracking-only behavior.

`GET /session/:sessionID/goal/stop` reads the latest saved result without retrying cancellation, repairing records, or changing tracking. It scans only that session's receipt namespace with at most four concurrent reads and orders by original request time with an intent tie-breaker. A newer requested/cleared result remains visible ahead of older completed results. Receipt identities must match their storage keys; malformed or misplaced records fail the lookup instead of falling back to a potentially misleading older success.

When the extension confirms that a session has no current goal, it fetches that read-only result and sends a separate historical notice with its request time. The banner ignores historical notices for another session or while a current goal or goal-edit/stop operation is displayed. A delayed history response therefore cannot erase a newly shown goal. Requested and cleared records explicitly retain their uncertainty. Full stop-history browsing, receipt retention, automatic reconciliation of uncertain external operations, shell/queued cancellation and cross-process ownership remain open.

## Verification limits

The session run-state service exposes a read-only observation of its current runner. Running work is identified by the runner's actual completion handle; shell work by its cancellation handle. Queued work keeps its identity when the shell finishes and the run starts. Stopping a waiter does not change the worker identity, and a replacement run receives a different ID. Startup uses the observed idle phase for eligibility. These UUIDs are process-local and held in weak references. A started dispatch can retain its observed worker ID, but the live handle lookup does not survive backend restart and does not cover independently managed background tools. The internal conditional running-worker cancellation described above is available; connecting it to goal stop with current ownership checks remains open.

The continuation handoff now receives the Effect cancellation signal and passes it to the application runtime request, including when interruption occurs while its modules are loading. Cooperative handoffs can observe cancellation; the goal is not marked finished or failed merely because the waiting fiber stops. The session runner owns an independently scoped execution fiber: interrupting its request waiter does not itself cancel that worker or external tools. The conditional running-worker primitive below can stop a matching observed execution, but wiring owned goal interruption to it and terminal reconciliation remain required before treating interruption as confirmed termination.

Recovery rechecks an acknowledged completed dispatch against the current conversation even when its accounting receipt is already saved. The exact assistant, unchanged completion timestamp, reserved user message, successful terminal state and absence of pending/running tools must still agree. A different user message newer by ID or queue timestamp prevents resumption of that old turn. This check is read-only and shares the acknowledgement validator. It does not lock the conversation across subsequent queue creation, so further coordination with input arriving during recovery remains necessary.

For the same goal direction, resume also handles a completed dispatch already acknowledged before an interruption. It records any missing turn accounting before queuing work, and uses the saved exact user/assistant receipt to avoid accounting twice when that write already succeeded. Recorded error/interrupted outcomes do not enter this ordinary resume path. A legacy finished record without an assistant identity cannot authorize recovery. This supports reopening at acknowledgement/accounting boundaries; it does not make the separate writes atomic or establish that external operations stopped.

Resume can reconcile a started dispatch from its latest saved matching assistant when the closing event was missed. It uses the same terminal-evidence validator as live acknowledgement, then the existing idempotent turn accounting and continuation eligibility checks. Missing, unfinished, pending-tool or errored evidence cannot authorize another automatic attempt through this path. A changed direction is still handled by the existing control-revision policy. Workspace startup invokes this resume path for eligible idle sessions; it does not query external operation handles. Acknowledgement, accounting and the next dispatch remain separate guarded writes; crash recovery between those writes is still incomplete.

Continuation queue creation reuses an existing queued dispatch for the same goal direction without another usage increment or storage revision. A started dispatch with that direction is left intact and cannot be replaced through ordinary continuation/resume. A corroborated finished dispatch or an explicit new goal direction permits a new queue item. This preserves unknown outcomes for reconciliation rather than treating a resume request as proof that an earlier worker stopped. Provider-error recovery retains its separate, bounded retry path. Startup handle reconciliation and automatic recovery of abandoned handoffs are not yet implemented.

Repetition detection compares earlier tool results with current work using the actual parts from the same transcript snapshot. Reused provider call IDs do not hide earlier results. Identical tool/input/result fingerprints can stop an automatic continuation; changed results remain eligible as progress under the existing rules.

Exact identity proves which persisted result the validator examined. It does not prove semantic relevance, that an artifact is unchanged since the check, that a person approved a judgment call, or that every external effect completed. Evidence revisions, stronger verification methods and human-review records remain part of the goal overhaul. Routine outcome summaries currently preserve evidence summaries; richer navigation to exact source results remains unfinished.

Identified error notifications now use the named assistant record for error detail. They cannot consume retries if that record has no saved error, belongs to another dispatch user message, or has been superseded by a newer assistant reply to the same user. Events without message identity retain legacy recovery behavior. This does not independently establish the state of external operations after a turn error or interruption.

## Saved goal work plans

Goals can retain a work plan alongside the full objective and acceptance criteria. The model-facing `update_goal_plan` tool requires the current goal intent and saved plan revision from `get_goal` (`null` for a first plan). Updates store the entire task list, with 1–100 tasks, unique stable IDs, descriptions, expected outputs, planned owners, verification instructions, statuses and dependencies.

The service rejects missing, repeated or cyclic dependencies. A task cannot be recorded as in progress or completed until its prerequisites are recorded as completed. Independent tasks may be in progress together. Storage revision checks reject conflicting updates. Repeating an identical plan for the same objective preserves the plan revision.

The extension shows this saved plan instead of session-wide todos when present, and includes it in copied goal reports. Task details use native expandable controls. Steering preserves the plan's original objective and displays a review warning until the plan is reconciled. Completed-goal history retains the selected goal's plan; old records without plans remain readable.

These are planning records, not worker leases, delegation authorization, scheduler state or evidence receipts. A planned owner is descriptive text. Declared task completion does not complete a goal, and plan-control calls cannot provide goal-completion evidence. The graph does not semantically verify task outputs, infer dependencies, or preserve every intermediate plan revision. Existing bounded goal-history retention still applies. The UI has source-level DOM verification; a packaged-extension visual and keyboard walkthrough remains outstanding.

## Auxiliary model selection

When a selected provider has no recognized small-model family, auxiliary model discovery now returns no substitute. The existing title, branch-name, commit-message, prompt-enhancement and project-copy callers then use their selected or configured fallback model. Discovery no longer sends that work to Kilo merely because its small model exists in the catalog. Selecting Kilo still permits Kilo's own small model, and explicit `small_model`, agent-model and plugin choices retain their existing precedence.

This change prevents an implicit provider switch; it does not establish a complete provider authorization policy or cost budget. A selected main model may cost more than a separately configured small model. Auto's orchestration-model policy, per-task routing provenance, capability constraints and cross-provider consent controls remain broader audit work.

The goal-plan tool also survives Auto's bounded tool filter in every workflow phase. Registration and a permission entry alone were insufficient because the runtime applies that additional filter before exposing tools to the model.

## Editing acceptance criteria

The goal's Steer editor can now add or revise acceptance criteria alongside the objective. Each row has a description and a verification method, and retains its stable ID across text edits. Criteria default to required; the user can explicitly mark a criterion optional. A configured list must retain between 1 and 20 nonblank criteria; the editor does not silently remove the whole acceptance contract. Legacy goals without structured criteria remain editable and can acquire a list.

Criteria updates use the goal-control API with the reviewed intent. Missing or stale revisions are rejected, including criteria-only requests. A changed list preserves the earlier requirements and their audit records, rotates the goal intent, clears the current completion audit and attempt, and marks any saved work plan for review. Objective-only changes still preserve criteria. Paused goals remain paused. The plan remains visible as a planning record; resaving it against the current intent reconciles its review flag and produces a new plan revision.

The client validates the draft and checks the response's criteria against the requested list before showing success. An uncertain or mismatched response keeps the editor's draft available for copying and review. Criteria changes do not bypass evidence checks or create a human acceptance record. Earlier versions are now retained as described below; authenticated person attribution remains outstanding.


## Required and optional goal outcomes

The goal editor labels each criterion Required or Optional. Legacy criteria without a flag remain required. The flag belongs to the saved goal contract and participates in edit acknowledgement checks; the completion tool cannot redefine it in an audit. Routine output contracts retain their existing required-only schema.

A completion audit must still account for every saved criterion exactly once using its original ID and description. Required criteria must pass with eligible evidence. An optional criterion may be reported unverified with `passed: false` and an empty evidence list. It remains visible in the accepted audit and report without a success indicator. If an optional criterion is claimed to pass, it receives the same evidence, artifact-freshness and command/smoke validation as required work. Unsupported evidence references cannot be attached to an unverified optional outcome.

A report with no requirement supported by verified work is rejected. Required failures, omitted or duplicate criteria and fabricated optional successes also remain rejected. The full objective remains authoritative; optionality does not authorize dropping other obligations, and human-judgment acceptance still needs a separate review contract.

### Routine result criterion outcomes

Settled routine results retain the accepted goal audit's timestamp and per-requirement description, criterion ID, required/optional classification, saved verification method and evidence summaries. A required flag omitted in a legacy goal remains required. Optional unverified outcomes retain an empty evidence list. The existing flattened evidence list remains for compatibility.

The run review presents the saved criterion outcomes for both live and archived routines through the same component. It identifies these as historical checks, separate from current verification and user acceptance. Older results without this record explicitly say criterion outcomes were not recorded and retain their original evidence summaries. Later goal changes do not rewrite an already settled result.

This is a result summary, not a second evidence authority. Original call identities, receipts and artifact freshness checks remain in the retained goal and conversation; opening that conversation is still necessary to inspect the source evidence. The record reflects the goal contract at settlement, which can differ from the original routine instructions shown separately. Routine creation still uses required-only output criteria. No automatic backfill of old results or new human-acceptance policy is introduced.
### Earlier requirement versions

Substantive objective or criteria changes now save the previous objective, criteria, plan, accepted audit and last audit attempt in the same guarded goal-state write. Each retained version has a stable ID, replacement timestamp, prior intent when available, and entry point (conversation steering or goal controls). No-op edits and status-only changes do not add versions. Invalid or stale edits cannot append a version. Prior versions are retained when a completed goal moves into the goal carousel.

Earlier requirements are reviewable in both current and archived goal views and copied reports. Rejected claims remain labeled rejected; previously accepted evidence is historical and does not satisfy the revised goal. Source requests identify the parent goal and exact version. Missing or duplicate versions fail rather than selecting another audit; receipt checks use the selected version's accepted audit. Routine goal refreshes preserve the selected archived goal instead of resetting its carousel position.

The entry point is not a verified person identity. Pre-existing lost versions are not reconstructed. This does not record every intermediate plan revision, every audit attempt within an unchanged contract, or human acceptance. Versions currently travel with the parent goal record, without a separate paginated store or independent retention policy; existing goal deletion/retention behavior still applies. Scalable history storage and authenticated authorship remain open parts of the full audit.
## Explicit review before goal completion

A criterion can now require review through the Steer editor's review checkbox. This requirement is saved separately from required/optional classification. When a completion audit passes for a criterion marked for review, Raya saves the evidence and pauses with Ready for review. It does not complete the goal or mark a linked self-heal verified.

Accept reviewed goal submits the current goal intent through the goal-control API. Acceptance rejects missing/stale intent, mixed requirement edits, goals without pending review, failed checks, stale artifacts, and evidence whose source digest changed after review was requested. It then records accepted status and time and completes the goal. Resume cannot bypass review: another successful completion submission pauses for review again. Optional unverified criteria remain unverified; they do not require acceptance of a claimed result.

The current view, earlier requirements, archived goals and copied reports retain review outcomes. Pending criteria do not receive completed success styling. Acceptance is a goal-control record, not authenticated person attribution; the model completion tool cannot submit acceptance. This does not infer which requirements need human judgment, provide reviewer identities, or change routine creation's required-only contract. These capabilities remain separate audit work.
